# 2026.286.1903 — docs(repo-setup): a root-module landing is tagged at the next validator, not at the merge (sdk#373)

## Summary

`sdk#373` asked whether a merge that produced no merge-time tag was a defect. It was not — and the answer was in that repo's own workflow file:

```
sdk/.github/workflows/tag-on-merge.yml (header) — measured:
  # `on: push` / `pull_request: [closed]` CANNOT see auto-merge merges: GitHub Actions creates ZERO workflow runs
  # for them (API-confirmed). Platform-level suppression.
  # `workflow_run` on `charly/pr-validator` is the ONE trigger whose event delivery is proven.
  # The org reusable sweep is idempotent and scans the last 24h of merged PRs, so any PR missed by a wait timeout
  # self-heals on the next validator completion.
```

This skill already told those repos *which tag form* they get (`v0.<YYYYDDD>.<HHMM>`) and said nothing about **when** it arrives. It does now, in the `repo-setup` entity: **a landing in `sdk`, `spec` or `plugin-gh` is tagged when the NEXT validator completes in that repo, not at the merge instant** — so a missing tag minutes after a merge there is expected, not a defect.

**And the corpus-generation gate, stated as the measured fact it now is rather than deferred:** this repo's corpus is generated from **pinned, tagged** refs — `charly marketplace generate` resolves a family's skills from the collected kindSet (`candy/plugin-marketplace/model.go`'s `buildModel` iterates `ks.Skills`), and the emitter writes each `s.Content` verbatim (`emit_skills.go`). **The pin therefore has to point at a tag that CONTAINS this change, which cannot exist before the change lands.** Producer-first is not a convention here; it is the only order the pipeline permits, and the refs pin advances at/after merge (manually or by the daily refresh), after which the drift gate regenerates the corpus. **This PR is the producer; it deliberately contains no regenerated corpus.**
