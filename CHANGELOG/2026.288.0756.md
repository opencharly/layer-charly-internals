### What the new reference states

**The intent model, and the two structural rules.** Every pin declares WHY it holds the value it does. `upstream:<ref>` is a **LEAF** — the owning repo's own ref, read from the REMOTE, so no local state can enter the answer and a leaf cannot inherit another repo's staleness. `derived-from:<path>` — and every `pin_map` entry, which desugars to exactly that — is an **EDGE**: the value is that path's recorded gitlink HERE. The two rules that make the graph judgeable: **an edge may not point at another edge** (depth ≤ 2, acyclic by construction — and the check covers EVERY edge source, `pinned_from` *and* each explicit `derived-from:<path>`), and **every leaf must be remote-verifiable**. A path with neither an intent nor a `branch=` is `unpinned` and is reported as such, never silently treated as a leaf; a path with no `intent:` but WITH a `branch=` does have one, implicit, because that is what `bump` does with it.

**The named states, and what each obliges.** `cur` obliges nothing. `behind` — a leaf whose recorded commit is an ancestor of the served ref — is an advance available NOW. `blocked-by <source>:<twin> (<state>)` names the producer that must go first: it cannot be advanced from here. `not-on-the-served-line` is explicitly **not** a divergence, and the reason is recorded: charly's history is squash-merged, so a pin taken before a merge is unreachable from the served ref while the tree is perfectly healthy — and a hand-pin to an unrelated commit yields the SAME two SHAs, so the report is the class plus the ONE remedy right for both.

**Why `behind` and `blocked-by` PASS by design.** *The FAIL set is structural only, and "structural" now has a precise meaning: what fails is a pin the workflow cannot JUDGE, or two sides that DISAGREE.* Everything it CAN judge and finds merely not-yet-advanced passes and is reported. Failing on a cross-repo leg would make the gate permanently red on a healthy tree, which is the mirror problem inverted — and the Message therefore **leads with the count of pins that are NOT current**, so a green run can never read as "everything is fine". The single exception is stated as its own row, because the obvious reading of "`blocked-by` passes" is wrong there: a `blocked-by` that names **no leg** — a source that is not a declared pin, or a twin its source declares no `branch=`/`url=` for — IS structural, since there is no producer to wait for.

**The producer-first leg order.** The Message ends with `producer-first legs:` — the leaves that can advance now, as `<path> (<recorded> -> <served>)`, then the edges those leaves unblock, joined with `->`. The two degenerate readings are DISTINCT and both are documented: `none — every pin is at the ref its intent names` (nothing is stale) versus `none reachable from this repo` (this repo HAS stale pins and every one is blocked by a producer it cannot reach).

**The one place the verb must stay blind.** The pin verb is domain-neutral by rule — paths, gitlinks, refs, and nothing about what a submodule CONTAINS — so a fact about a repository's own composition is that repository's gate's to own. That is stated once, in the last bullet, pointing at `umbrella-mechanics` rather than restating it.
