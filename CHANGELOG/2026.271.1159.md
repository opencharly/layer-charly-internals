## Summary

### The harness constraint — stated plainly
An agent is woken **only when a background command COMPLETES**. So a watcher (or a `while true` loop) that never exits gives **no wake**, and a one-shot watcher that exits leaves **nothing watching** until an agent re-arms it. The correct architecture: **each wake is produced by a finite watcher run, and a successor is already armed before the wake lands.**

### The two supported patterns
| Pattern | How | Use when |
|---|---|---|
| **per-event notify** (`--no-rearm`, default) | one-shot; the AGENT re-arms on each wake | the agent must act on every event |
| **durability** (`--auto-rearm`) | on a non-terminal exit the watcher **detaches a lock-guarded successor with the SAME args BEFORE it prints + exits** | a STANDING watch that must survive fires independent of the agent |

`--auto-rearm` keeps a **watch** alive; the agent's re-arm keeps **notifications** alive. A durable supervisor never exits ⇒ never wakes, so it is **NOT** the answer (documented explicitly).

### The re-arm INVARIANT
An agent that acts on a wake **MUST** leave a watcher armed — `--auto-rearm` makes it automatic; a per-event agent re-arms in the same turn it acts. An agent that fires an event and does not re-arm has silently stopped watching (the failure this family exists to remove).

### Also documented
- **Single instance:** a per-args flock lockfile + holder PID — repeated arms never stack; a foreground arm takes over a live peer cleanly.
- **Rate-limit discipline:** read the FREE `/rate_limit` quota before each poll; below `WATCH_RATE_MIN` back off (4×, capped) instead of hammering into the observed HTTP-403 wall.
