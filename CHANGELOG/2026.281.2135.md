# 2026.281.2135 — docs(git-workflow): add the backticked-closing-keyword trap

## Summary

One bullet, from a failure measured tonight: **a closing keyword inside backticks does not close an issue.**

GitHub's closing-keyword parser ignores a code-formatted reference, so a PR body carrying `` Closes `<owner>/<repo>#N` `` **merges the PR and leaves the issue OPEN** - silently, with no error anywhere. It happened on a fully green cutover (`opencharly/charly#863`, MERGED, `v2026.281.2127`) whose issue stayed open across its own merge.

**The remedy is stated with the trap, because the trap is invisible:** verify the **ISSUE**, not only the PR - *a merge and a closure are two artefacts* - and repair a missed closure with a `RESOLVED` comment naming the merged PR **and** the merge tag, then close. That is exactly what was done, and it is why the issue is closed rather than quietly open.

It sits with the body-evidence rules, because that is what it is: a claim in a PR body that does not do what it says.
