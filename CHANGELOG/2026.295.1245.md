# 2026.295.1245 — docs(repo-setup): a fork is a legitimate repo, not a landing prohibition

## Summary

A session read `charly-internals:repo-setup` and concluded that a forked repo in the opencharly org is a defect that cannot land a PR. The skill said an excluded repo "receives NEITHER the org workflow NOR CalVer tags — by design, not by omission", and later grouped a fork with a vendored upstream and an artifact-branch sink under "Excluded BY DESIGN (no tag expected)". Neither sentence said what an excluded repo does instead, so "not covered by the org validator" read as "cannot land".

Both halves are false, and the live org shows it:

- `openclaw-enterprise` is a fork, has ZERO branch rules, and lands on its own `.github/workflows/ci.yml`; PR #2 merged 2026-10-13 with `CI Required`, `CodeQL` and `QA advisory`, and no `validate / validate`.
- `crabbox` is a fork, is excluded from the org-wide ruleset, and carries its own repo-scoped ruleset requiring the SAME `org-wide-pr-validator-required.yml`.
- `gst-wayland-display` is a fork on a non-`main` default (`stable`), carries its own rules there including `validate / validate`, and already has three CalVer tags minted out-of-band.

The fix keeps every real rule: a NEW repo is still created non-fork so it inherits the org gate; an excluded repo still does not get an automatic CalVer tag. What changes is the false implication that exclusion forbids landing, plus the category error that put a developed fork in one bucket with a vendored upstream and an artifact sink.
