# 2026.260.2019 — docs(git-workflow): an empty commit DOES re-trigger — measured; the dispatch does not clear the rollup

## Summary of changes

The `/charly-internals:git-workflow` skill (owned by this repo, family `internals`) contradicted
itself on validator re-triggering — and the side that was wrong was the load-bearing one for
body-only fixes:

- the "Validator re-trigger" bullet said: *"An empty commit does NOT re-trigger `pr-validator`.
  The pull_request workflow ignores pushes with no diff."*
- the "Non-negotiable invariants" bullet said: *"`git commit --allow-empty` with a docs message is
  the standard append-only re-trigger."*

Both cannot hold. Measured directly on two PRs (R1):

- `opencharly/plugin-pipeline#28` — the empty commit `be3ab30` produced a fresh
  `charly/pr-validator` run `ev=pull_request` keyed to `be3ab30` (run `35266814709`,
  created 19:46:00Z), and the PR merged on that head.
- `opencharly/plugin-vm#35` — the empty commit `57ddafe` likewise produced a fresh
  `ev=pull_request` run (`35266917620`), and the PR merged on that head.

The dispatcher has no diff guard: `.github/workflows/pr-validator.yml` is
`on: pull_request: types: [opened, synchronize, reopened, ready_for_review]` with no
`paths:`/`paths-ignore`. A no-content push therefore fires `synchronize` normally.

**What is also measured:** a `gh workflow run pr-validator.yml -f pr-number=<N> --ref <branch>`
re-runs on the SAME head, so GitHub's check rollup keeps BOTH check runs for the same check
name — a stale earlier `failure` can keep the PR `BLOCKED` even though the dispatched run is
green. Both were observed on `plugin-vm#35`/`plugin-pipeline#28`: the dispatched success did NOT
clear the rollup (which still read `FAILURE` from the earlier same-name run), whereas the fresh
SHA from an empty commit gave a clean single-run rollup. So the doc now prescribes the empty
commit for a body-only re-trigger and warns about the dispatch's rollup behavior.
