# 2026.281.1503 — docs(repo-setup)!: teach the class/naming step BEFORE a repo is created

## Summary

The class and naming contract now exists in two places: the **rule** in the umbrella `AGENTS.md` ("Repo classes and naming") and the **placement lines** in its org map (`README.md`, one per class). Both are referenced from this skill — what this PR adds is the part neither of them carries: **the procedure, run before the new-repo checklist**.

- A new **Step 0 — choose the class and the name** section in the `repo-setup` skill entity, placed ahead of `## Setting up a NEW repository (checklist)`. It walks the decisions in order: (1) what the entity is — the KIND axis; (2) which family it belongs to, which is also the skill namespace and the corpus directory; (3) which **single** repo owns it, per the rulebook's R3, with the others referencing it by `@github.com/<owner>/<repo>:<vX.Y.Z>` or a namespace import; (4) naming it by class — bare names for core/contract and appliances only, every other repo carrying its prefix, and a product family being a `layer-<family>` repo.
- It **points at the canonical tables rather than copying them**. That is deliberate and it is this repo's own rule ("do not restate the umbrella's rules here"): the class → name → "may hold" mapping lives in the umbrella `README.md`, verified by `./charly/bin/charly task org-map`, and the rule lives in `AGENTS.md`. A copy in a skill drifts; a pointer does not.
- The **worked counter-example is recorded**, because it happened: a product family created as a bare `openclaw`, holding a box, a candy, a disposable bed and two skills — a `layer-<family>` shape — renamed to `layer-openclaw`. A bare name holding more than core/contract or an appliance is exactly the defect this step catches.

**Scope and its one follow-up, stated plainly:** the projected corpus file (`internals/skills/repo-setup/SKILL.md`) is **generated** from this entity, so it is not hand-edited here — and a hand-edited copy would be stale on arrival. Its regeneration is **routed to M7**, this cutover's named corpus step, which is where the pin advance and the regeneration both live: the marketplace projects this skill once this repo is pinned at its post-merge tag. Nothing else in this repo changes — no candy content, no plan step, no pin.
