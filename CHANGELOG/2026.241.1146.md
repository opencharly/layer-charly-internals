# 2026.241.1146 — feat: the charly-internals concept candy as a standalone repo

## Summary of changes

Phase D of the approved cutover, first repo: extract the `charly-internals` concept candy out of
`charly/candy/` into its own kind-prefixed repo.

`charly/candy/` is the corpus's **second input path** — it reaches the marketplace only because CI
clones charly at a hand-written tag, which is how a stale pin can freeze skill content while every
gate stays green. Emptying it removes that path. This candy owns **18 `skill:` entities** of the
`internals` family, one of five families sourced *entirely* from `charly/candy/`.

Contents — the canonical standalone candy layout:

| File | Notes |
|---|---|
| `charly.yml` | the candy **verbatim** from `charly/candy/charly-internals/charly.yml`, with the file-level `version:` line prepended |
| `README.md` | states this is a concept candy and that `SKILL.md` is generated, not edited here |
| `.github/workflows/{deploy,pr-validator,tag-on-merge}.yml` | the standard three dispatchers |

**No skill content is edited.** The move must be byte-identical in the corpus — that is the gate,
and it only means anything if the move is a pure copy. Content corrections (this candy's
description still carries a stale `candy/plugin-marketplace` reference) follow separately, after
the move is proven.

### Two stale values deliberately NOT copied from the template

Every existing candy repo declares `version: 2026.232.0520` and pins CI at charly
`v2026.238.1242`. Both are stale: current charly requires schema **`2026.240.1943`**, and the
repos stay green only *because* their CI pin is old enough not to notice. Copying the template
verbatim would have imported both. This repo declares the current schema and pins the current
charly tag (`v2026.241.1121`).

That the ~170 existing repos sit on an outdated schema behind stale pins is a real finding; it is
not fixed here (it is the named follow-on batch in the plan), but it is not propagated either.
