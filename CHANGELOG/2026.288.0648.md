### What was wrong (both measured on the umbrella, 2026-10-15)

- **`task sync` was described as a "preview", and the `task prune` row told the reader to pass `MODE=report` for a dry run.** The declared `MODE` param DEFAULTS to `report`, so plain `charly task prune` IS the dry run — while the quoted form is REJECTED:

  ```
  $ charly task prune MODE=report
  charly: error: command "task": unexpected extra argument "MODE=report" (only one task name)
  rc=1

  $ charly task prune
  task prune: 1 step(s), 0 failed
    [pass] run — prune merged-upstream worktrees and branches across the umbrella + submodules
  rc=0
  ```
  `sync` also does more than decline to commit: it MATERIALISES each advanced checkout (`switch --quiet --detach`) and STAGES its gitlink (`git add <path>`).

- **`verify` was presented as "the full pinning gate" with nothing said about what it does NOT answer.** MEASURED: its pinning steps were GREEN on a tree where **five of the six `distro-*` gitlinks were behind their remote `main`** (`verify: 0 policy pin(s) hold across 429 submodule(s); 422 checkout(s) clean at their gitlink; 7 uninitialized`).

### What was missing, and is now stated

- **The three questions, and which of them has a verb.** STATE = `charly task map`. CONSISTENCY = `charly task verify`, with its commit-time half `charly task policy-b`. **CURRENCY has NO verb at all** — it must be MEASURED, gitlink against the owning repo's remote default-branch HEAD. A green `verify` is not a currency claim, and the honest form of a currency claim is a table of `<path>: <recorded gitlink> vs <remote default-branch HEAD>`.
- **Policy B is a consistency contract, not a currency one** — it holds while both sides are equally stale. `sync` pins `distro-*` FROM charly's own nested `box/*` gitlinks, so when those are behind, the umbrella's pins equal them exactly and policy B passes. The umbrella CANNOT advance those five from here: the only sanctioned writer of a `distro-*` pin is the verb, and the verb's source of truth is that same stale gitlink. Advancing them is a change in `opencharly/charly`.
- **`task sync`'s answer is base-relative.** It must run on a checkout current with `origin/main`, or its "advances" are diffs against a dead base — measured: 22 reported from a clone on `b730035`, of which only **10** were genuine against `origin/main`. Its selection is also PARTIAL when the tree is not fully initialized (`charly#917`).
- **The `sync` ↔ commit-gate seam, and what to do about it.** The pair is coherent at `sync`'s exit and conflicts the moment the advances are UN-STAGED while the checkouts stay advanced — which the sanctioned branch flow does by design (`git switch -c <b> origin/main`, `git reset`, `git stash pop`, an aborted commit). The direction and the remedy now ship in the verb (`plugin-task#27`), and the section names the pre-fix symptom so an older tree can still be read.
- **A fresh session worktree cannot run `sync` to a green exit, by design** (`#469`): `bump` skips every `.gitmodules` path with no checkout and then FAILS the run, naming them. The bump is real and committable — `verify` classifies the same paths as *uninitialized (pin audited, no checkout)* and can PASS — so read the reported set, not the exit code.
- **Nothing locks the shared checkout** (one index, N sessions): check the process table for an in-flight `task sync` before measuring or staging.
- **A pin advance that brings in a NEW marketplace corpus family must bind it in BOTH harness-config surfaces in the same commit** — `reasonix.toml`'s `[skills] paths` and the tracked `.dsh/skills/<name>` symlink farm — or the family loads as ZERO skills, silently. `charly task verify` is what enforces it, including the follow-on signal that its `--self-test` then reports *"the unmutated copy of this tree is not green"* (a consequence of the same missing rows, not a third defect).
